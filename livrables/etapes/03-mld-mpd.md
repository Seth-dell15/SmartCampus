# SmartCampus — Étape 3 : MLD / MPD

## 1. Objet et choix techniques

Ce livrable dérive le Modèle Logique de Données (MLD) et le Modèle Physique de Données (MPD) du MCD de l’étape 2. Il présente le schéma relationnel, les clés, les contraintes d’intégrité, une stratégie d’indexation et un DDL PostgreSQL cohérent.

### Hypothèses physiques

- **SGBD cible : PostgreSQL 15 ou ultérieur.** Le DDL utilise `TIMESTAMPTZ`, les tables partitionnées, `INCLUDE` dans les index, et l’extension standard `btree_gist` pour interdire les chevauchements d’intervalles temporels.
- Les noms SQL sont en `snake_case`, sans accents; les identifiants techniques sont des `BIGINT GENERATED BY DEFAULT AS IDENTITY`.
- Les instants sont enregistrés en `TIMESTAMPTZ` et interprétés en UTC. Les intervalles d’affectation sont semi-ouverts `[début, fin[`.
- Les dictionnaires de statuts sont ici contrôlés par `CHECK`; ils pourront évoluer vers des tables de référence si l’application doit administrer ces valeurs.
- La table `mesure` est partitionnée par mois sur l’horodatage d’événement. Pour satisfaire la contrainte PostgreSQL imposant que toute clé unique d’une table partitionnée inclue sa clé de partition, sa PK physique est composée de `(horodatage_evenement, id_mesure)`. `id_mesure` reste l’identifiant conceptuel; les références physiques vers une mesure transportent aussi son horodatage.

La stratégie de partitionnement est un choix MPD de capacité, pas un changement du sens métier du MCD.

## 2. Modèle Logique de Données (MLD)

Notation : `PK` = clé primaire, `FK` = clé étrangère, `UQ` = unicité, `NN` = non nul. Les associations simples deviennent des clés étrangères; les associations porteuses d’attributs deviennent des tables.

```text
CAMPUS(
  PK id_campus,
  UQ code_campus,
  nom, adresse, statut
)

BATIMENT(
  PK id_batiment,
  FK id_campus -> CAMPUS.id_campus,
  UQ code_batiment,
  nom, adresse, statut
)

ZONE(
  PK id_zone,
  FK id_batiment -> BATIMENT.id_batiment,
  UQ (id_batiment, code_zone),
  nom, type_zone, etage, statut
)

EQUIPEMENT(
  PK id_equipement,
  UQ code_equipement,
  libelle, type_equipement, marque, modele, numero_serie,
  date_mise_en_service, statut
)

HISTORIQUE_ZONE_EQUIPEMENT(
  PK id_historique_zone,
  FK id_equipement -> EQUIPEMENT.id_equipement,
  FK id_zone -> ZONE.id_zone,
  date_debut, date_fin, motif_deplacement,
  CHECK date_debut < date_fin si date_fin renseignée,
  EXCLUSION : intervalles d’un même équipement non chevauchants
)

CAPTEUR(
  PK id_capteur,
  UQ identifiant_externe,
  type_capteur, libelle, unite_nominale, statut, date_mise_en_service
)

AFFECTATION_CAPTEUR_EQUIPEMENT(
  PK id_affectation_capteur,
  FK id_capteur -> CAPTEUR.id_capteur,
  FK id_equipement -> EQUIPEMENT.id_equipement,
  date_debut, date_fin, motif_affectation,
  CHECK date_debut < date_fin si date_fin renseignée,
  EXCLUSION : intervalles d’un même capteur non chevauchants
)

MESURE(
  PK physique (horodatage_evenement, id_mesure),
  id_mesure, FK id_capteur -> CAPTEUR.id_capteur,
  horodatage_evenement, horodatage_reception,
  valeur, unite, qualite, cle_deduplication
)

REGLE_ALERTE(
  PK id_regle_alerte,
  UQ (code_regle, numero_version),
  libelle, portee_cible, indicateur, operateur, seuil, severite,
  date_debut_validite, date_fin_validite, statut
)

ALERTE(
  PK id_alerte,
  FK id_regle_alerte -> REGLE_ALERTE.id_regle_alerte,
  FK id_equipement_cible -> EQUIPEMENT.id_equipement NULL,
  FK id_capteur_cible -> CAPTEUR.id_capteur NULL,
  FK (horodatage_mesure_declencheuse, id_mesure_declencheuse)
     -> MESURE(horodatage_evenement, id_mesure) NULL,
  date_creation, severite_constatee, statut,
  date_acquittement, date_cloture, commentaire,
  CHECK : exactement une cible (équipement XOR capteur)
)

UTILISATEUR(
  PK id_utilisateur,
  UQ courriel,
  prenom, nom, statut, date_creation
)

TECHNICIEN(
  PK id_technicien,
  FK UQ id_utilisateur -> UTILISATEUR.id_utilisateur,
  UQ matricule,
  specialite, statut
)

INTERVENTION(
  PK id_intervention,
  UQ reference,
  FK id_equipement -> EQUIPEMENT.id_equipement,
  FK id_demandeur -> UTILISATEUR.id_utilisateur NULL,
  type_intervention, priorite, statut, date_ouverture, date_planifiee,
  date_debut, date_cloture, description, compte_rendu
)

AFFECTATION_TECHNICIEN_INTERVENTION(
  PK id_affectation_technicien,
  FK id_intervention -> INTERVENTION.id_intervention,
  FK id_technicien -> TECHNICIEN.id_technicien,
  date_affectation, date_fin_affectation, role_dans_intervention, commentaire
)

LIEN_ALERTE_INTERVENTION(
  PK id_lien_alerte_intervention,
  FK id_alerte -> ALERTE.id_alerte,
  FK id_intervention -> INTERVENTION.id_intervention,
  date_liaison, commentaire,
  UQ (id_alerte, id_intervention)
)
```

Le couple `(id_capteur, horodatage_evenement)` n’est pas déclaré unique pour une mesure : la précision d’horloge et la politique de déduplication restent à valider. Une éventuelle clé de message source devra être définie avec son périmètre et sa garantie d’unicité avant d’imposer une contrainte unique.

## 3. Modèle Physique de Données (MPD)

### 3.1 Choix des types

| Domaine | Type PostgreSQL | Motif |
|---|---|---|
| Identifiants techniques | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | Grande marge de capacité et génération intégrée. |
| Libellés et codes | `VARCHAR(n)` | Taille maximale explicite et validation des données de référence. |
| Notes / comptes rendus | `TEXT` | Longueur variable; aucun besoin d’indexer le texte complet dans le périmètre initial. |
| Valeurs mesurées / seuils | `NUMERIC(20,6)` | Précision décimale déterministe pour énergie et grandeurs techniques; la précision métier reste à confirmer par type de capteur. |
| Dates civiles | `DATE` | Mise en service sans heure utile. |
| Instants | `TIMESTAMPTZ` | Instants comparables et stockage cohérent malgré les fuseaux d’affichage. |
| États, unités et vocabulaires | `VARCHAR(n)` + `CHECK` | Contrôles simples au départ, sans créer une table de référence par vocabulaire. |
| Clé d’événement source | `VARCHAR(160)` | Transport d’un identifiant de message non numérique fourni par la passerelle. |

`NUMERIC(20,6)` est un compromis initial, à confronter à la précision requise des compteurs et à la taille effective des messages. Une unité canonique et les conversions doivent être définies par type de capteur avant les analyses multi-équipements.

### 3.2 Intégrité et contraintes temporelles

- Les associations obligatoires du MCD sont matérialisées par des clés étrangères `NOT NULL`; les associations facultatives par des clés étrangères nullables.
- Les intervalles sont valides si `date_debut < date_fin` lorsque la fin existe.
- Les contraintes d’exclusion GiST interdisent les périodes qui se chevauchent pour un équipement donné dans son historique de zone, et pour un capteur donné dans ses affectations à un équipement.
- Ces exclusions autorisent des intervalles ouverts et des intervalles consécutifs qui se touchent sans se chevaucher.
- L’alerte doit avoir exactement une cible (équipement ou capteur), vérifiée par un `CHECK`. Une validation déclencheur s’assure également que cette cible est compatible avec la portée de la version de règle.
- Les dates de fermeture, d’acquittement et d’affectation ne sont pas imposées par des `CHECK` de cycle de vie, car les transitions de statuts et leurs règles n’ont pas encore été arrêtées.
- Une contrainte FK assure qu’une mesure déclencheuse existe. Une contrainte métier ne vérifie pas automatiquement que l’horodatage de cette mesure tombe dans l’intervalle d’affectation capteur-équipement : cette association temporelle doit être résolue lors du traitement et, si nécessaire, matérialisée par le service d’alertes.

### 3.3 Script SQL de création

Le script suivant vise PostgreSQL 15+. Le bloc de partitions crée les partitions mensuelles du mois courant jusqu’à douze mois dans le futur. Il doit être exécuté et supervisé avant la première ingestion de chaque nouvelle période; une tâche de maintenance doit créer à l’avance les partitions suivantes et supprimer/archiver celles qui dépassent la rétention approuvée.

```sql
BEGIN;

CREATE SCHEMA IF NOT EXISTS smartcampus;
SET LOCAL search_path = smartcampus, public;

CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE campus (
    id_campus       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code_campus     VARCHAR(80)  NOT NULL UNIQUE,
    nom             VARCHAR(160) NOT NULL,
    adresse         VARCHAR(500),
    statut          VARCHAR(30)  NOT NULL
        CHECK (statut IN ('ACTIF', 'INACTIF', 'ARCHIVE'))
);

CREATE TABLE batiment (
    id_batiment     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_campus       BIGINT       NOT NULL
        REFERENCES campus (id_campus) ON UPDATE RESTRICT ON DELETE RESTRICT,
    code_batiment   VARCHAR(80)  NOT NULL UNIQUE,
    nom             VARCHAR(160) NOT NULL,
    adresse         VARCHAR(500),
    statut          VARCHAR(30)  NOT NULL
        CHECK (statut IN ('ACTIF', 'INACTIF', 'ARCHIVE'))
);

CREATE TABLE zone (
    id_zone         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_batiment     BIGINT       NOT NULL
        REFERENCES batiment (id_batiment) ON UPDATE RESTRICT ON DELETE RESTRICT,
    code_zone       VARCHAR(80)  NOT NULL,
    nom             VARCHAR(160) NOT NULL,
    type_zone       VARCHAR(50)  NOT NULL,
    etage           VARCHAR(40),
    statut          VARCHAR(30)  NOT NULL
        CHECK (statut IN ('ACTIVE', 'FERMEE', 'ARCHIVEE')),
    CONSTRAINT uq_zone_batiment_code UNIQUE (id_batiment, code_zone)
);

CREATE TABLE equipement (
    id_equipement           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code_equipement         VARCHAR(100) NOT NULL UNIQUE,
    libelle                 VARCHAR(200) NOT NULL,
    type_equipement         VARCHAR(80)  NOT NULL,
    marque                  VARCHAR(100),
    modele                  VARCHAR(100),
    numero_serie            VARCHAR(120),
    date_mise_en_service    DATE,
    statut                  VARCHAR(30)  NOT NULL
        CHECK (statut IN (
            'EN_PREPARATION', 'EN_SERVICE', 'HORS_SERVICE', 'RETIRE', 'ARCHIVE'
        ))
);

CREATE TABLE historique_zone_equipement (
    id_historique_zone  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_equipement      BIGINT       NOT NULL
        REFERENCES equipement (id_equipement) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_zone            BIGINT       NOT NULL
        REFERENCES zone (id_zone) ON UPDATE RESTRICT ON DELETE RESTRICT,
    date_debut         TIMESTAMPTZ  NOT NULL,
    date_fin           TIMESTAMPTZ,
    motif_deplacement  VARCHAR(500),
    CONSTRAINT ck_hze_intervalle
        CHECK (date_fin IS NULL OR date_debut < date_fin),
    CONSTRAINT ex_hze_equipement_periode
        EXCLUDE USING gist (
            id_equipement WITH =,
            tstzrange(date_debut, date_fin, '[)') WITH &&
        )
);

CREATE TABLE capteur (
    id_capteur           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    identifiant_externe  VARCHAR(160) NOT NULL UNIQUE,
    type_capteur         VARCHAR(80)  NOT NULL,
    libelle              VARCHAR(200) NOT NULL,
    unite_nominale       VARCHAR(30)  NOT NULL,
    statut               VARCHAR(30)  NOT NULL
        CHECK (statut IN ('EN_STOCK', 'EN_SERVICE', 'INDISPONIBLE', 'RETIRE', 'ARCHIVE')),
    date_mise_en_service DATE
);

CREATE TABLE affectation_capteur_equipement (
    id_affectation_capteur BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_capteur             BIGINT       NOT NULL
        REFERENCES capteur (id_capteur) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_equipement          BIGINT       NOT NULL
        REFERENCES equipement (id_equipement) ON UPDATE RESTRICT ON DELETE RESTRICT,
    date_debut             TIMESTAMPTZ  NOT NULL,
    date_fin               TIMESTAMPTZ,
    motif_affectation      VARCHAR(500),
    CONSTRAINT ck_ace_intervalle
        CHECK (date_fin IS NULL OR date_debut < date_fin),
    CONSTRAINT ex_ace_capteur_periode
        EXCLUDE USING gist (
            id_capteur WITH =,
            tstzrange(date_debut, date_fin, '[)') WITH &&
        )
);

CREATE TABLE utilisateur (
    id_utilisateur BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    courriel       VARCHAR(254) NOT NULL UNIQUE,
    prenom         VARCHAR(100) NOT NULL,
    nom            VARCHAR(100) NOT NULL,
    statut         VARCHAR(30)  NOT NULL
        CHECK (statut IN ('ACTIF', 'SUSPENDU', 'DESACTIVE')),
    date_creation  TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE technicien (
    id_technicien BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_utilisateur BIGINT NOT NULL UNIQUE
        REFERENCES utilisateur (id_utilisateur) ON UPDATE RESTRICT ON DELETE RESTRICT,
    matricule     VARCHAR(80) NOT NULL UNIQUE,
    specialite    VARCHAR(100),
    statut        VARCHAR(30) NOT NULL
        CHECK (statut IN ('ACTIF', 'INDISPONIBLE', 'INACTIF'))
);

CREATE TABLE regle_alerte (
    id_regle_alerte      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    code_regle           VARCHAR(100) NOT NULL,
    numero_version       INTEGER      NOT NULL CHECK (numero_version > 0),
    libelle              VARCHAR(200) NOT NULL,
    portee_cible         VARCHAR(20)  NOT NULL
        CHECK (portee_cible IN ('EQUIPEMENT', 'CAPTEUR')),
    indicateur           VARCHAR(80)  NOT NULL,
    operateur            VARCHAR(20)  NOT NULL
        CHECK (operateur IN ('>', '>=', '<', '<=', '=', '<>')),
    seuil                NUMERIC(20, 6) NOT NULL,
    severite             VARCHAR(30)  NOT NULL
        CHECK (severite IN ('INFO', 'MINEURE', 'MAJEURE', 'CRITIQUE')),
    date_debut_validite  TIMESTAMPTZ  NOT NULL,
    date_fin_validite    TIMESTAMPTZ,
    statut               VARCHAR(20)  NOT NULL
        CHECK (statut IN ('BROUILLON', 'ACTIVE', 'SUSPENDUE', 'EXPIREE')),
    CONSTRAINT uq_regle_alerte_version UNIQUE (code_regle, numero_version),
    CONSTRAINT ck_regle_alerte_validite
        CHECK (date_fin_validite IS NULL OR date_debut_validite < date_fin_validite)
);

CREATE TABLE mesure (
    id_mesure             BIGINT GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_capteur            BIGINT         NOT NULL,
    horodatage_evenement  TIMESTAMPTZ    NOT NULL,
    horodatage_reception  TIMESTAMPTZ    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    valeur                NUMERIC(20, 6) NOT NULL,
    unite                 VARCHAR(30)    NOT NULL,
    qualite               VARCHAR(30)    NOT NULL
        CHECK (qualite IN ('VALIDE', 'INVALIDE', 'ESTIMEE', 'INCONNUE')),
    cle_deduplication     VARCHAR(160),
    CONSTRAINT pk_mesure
        PRIMARY KEY (horodatage_evenement, id_mesure),
    CONSTRAINT fk_mesure_capteur
        FOREIGN KEY (id_capteur)
        REFERENCES capteur (id_capteur)
        ON UPDATE RESTRICT ON DELETE RESTRICT
) PARTITION BY RANGE (horodatage_evenement);

DO $partitionnement$
DECLARE
    debut_mois DATE := date_trunc('month', CURRENT_DATE)::date;
    borne_debut DATE;
    borne_fin DATE;
    nom_partition TEXT;
    decalage INTEGER;
BEGIN
    FOR decalage IN 0..12 LOOP
        borne_debut := (debut_mois + make_interval(months => decalage))::date;
        borne_fin := (debut_mois + make_interval(months => decalage + 1))::date;
        nom_partition := 'mesure_' || to_char(borne_debut, 'YYYY_MM');

        EXECUTE format(
            'CREATE TABLE %I PARTITION OF mesure FOR VALUES FROM (%L) TO (%L)',
            nom_partition,
            borne_debut,
            borne_fin
        );
    END LOOP;
END
$partitionnement$;

CREATE TABLE alerte (
    id_alerte                       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_regle_alerte                 BIGINT      NOT NULL
        REFERENCES regle_alerte (id_regle_alerte) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_equipement_cible             BIGINT
        REFERENCES equipement (id_equipement) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_capteur_cible                BIGINT
        REFERENCES capteur (id_capteur) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_mesure_declencheuse          BIGINT,
    horodatage_mesure_declencheuse  TIMESTAMPTZ,
    date_creation                   TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    severite_constatee              VARCHAR(30) NOT NULL
        CHECK (severite_constatee IN ('INFO', 'MINEURE', 'MAJEURE', 'CRITIQUE')),
    statut                          VARCHAR(30) NOT NULL
        CHECK (statut IN ('OUVERTE', 'ACQUITTEE', 'EN_COURS', 'CLOTUREE', 'IGNOREE')),
    date_acquittement               TIMESTAMPTZ,
    date_cloture                    TIMESTAMPTZ,
    commentaire                     TEXT,
    CONSTRAINT ck_alerte_cible_xor
        CHECK ((id_equipement_cible IS NOT NULL) <> (id_capteur_cible IS NOT NULL)),
    CONSTRAINT ck_alerte_mesure_declencheuse
        CHECK (
            (id_mesure_declencheuse IS NULL AND horodatage_mesure_declencheuse IS NULL)
            OR
            (id_mesure_declencheuse IS NOT NULL AND horodatage_mesure_declencheuse IS NOT NULL)
        ),
    CONSTRAINT fk_alerte_mesure_declencheuse
        FOREIGN KEY (horodatage_mesure_declencheuse, id_mesure_declencheuse)
        REFERENCES mesure (horodatage_evenement, id_mesure)
        ON UPDATE RESTRICT ON DELETE RESTRICT
);

CREATE TABLE intervention (
    id_intervention       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    reference             VARCHAR(100) NOT NULL UNIQUE,
    id_equipement         BIGINT       NOT NULL
        REFERENCES equipement (id_equipement) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_demandeur          BIGINT
        REFERENCES utilisateur (id_utilisateur) ON UPDATE RESTRICT ON DELETE RESTRICT,
    type_intervention     VARCHAR(30)  NOT NULL
        CHECK (type_intervention IN ('CORRECTIVE', 'PREVENTIVE', 'INSPECTION', 'AUTRE')),
    priorite              VARCHAR(30)  NOT NULL
        CHECK (priorite IN ('BASSE', 'NORMALE', 'HAUTE', 'URGENTE')),
    statut                VARCHAR(30)  NOT NULL
        CHECK (statut IN (
            'A_PLANIFIER', 'PLANIFIEE', 'EN_COURS', 'EN_ATTENTE', 'TERMINEE', 'ANNULEE'
        )),
    date_ouverture        TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    date_planifiee        TIMESTAMPTZ,
    date_debut            TIMESTAMPTZ,
    date_cloture          TIMESTAMPTZ,
    description           TEXT        NOT NULL,
    compte_rendu          TEXT
);

CREATE TABLE affectation_technicien_intervention (
    id_affectation_technicien BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_intervention           BIGINT      NOT NULL
        REFERENCES intervention (id_intervention) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_technicien             BIGINT      NOT NULL
        REFERENCES technicien (id_technicien) ON UPDATE RESTRICT ON DELETE RESTRICT,
    date_affectation          TIMESTAMPTZ NOT NULL,
    date_fin_affectation      TIMESTAMPTZ,
    role_dans_intervention    VARCHAR(40),
    commentaire               TEXT,
    CONSTRAINT ck_ati_intervalle
        CHECK (
            date_fin_affectation IS NULL
            OR date_affectation < date_fin_affectation
        )
);

CREATE TABLE lien_alerte_intervention (
    id_lien_alerte_intervention BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_alerte                   BIGINT      NOT NULL
        REFERENCES alerte (id_alerte) ON UPDATE RESTRICT ON DELETE RESTRICT,
    id_intervention             BIGINT      NOT NULL
        REFERENCES intervention (id_intervention) ON UPDATE RESTRICT ON DELETE RESTRICT,
    date_liaison                TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    commentaire                 TEXT,
    CONSTRAINT uq_lien_alerte_intervention UNIQUE (id_alerte, id_intervention)
);

CREATE OR REPLACE FUNCTION verifier_cible_alerte()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
DECLARE
    portee_attendue VARCHAR(20);
BEGIN
    SELECT r.portee_cible
      INTO portee_attendue
      FROM regle_alerte AS r
     WHERE r.id_regle_alerte = NEW.id_regle_alerte;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Regle d''alerte % inexistante', NEW.id_regle_alerte
            USING ERRCODE = 'foreign_key_violation';
    END IF;

    IF portee_attendue = 'EQUIPEMENT'
       AND (NEW.id_equipement_cible IS NULL OR NEW.id_capteur_cible IS NOT NULL) THEN
        RAISE EXCEPTION 'La regle % attend une cible equipement', NEW.id_regle_alerte
            USING ERRCODE = 'check_violation';
    ELSIF portee_attendue = 'CAPTEUR'
       AND (NEW.id_capteur_cible IS NULL OR NEW.id_equipement_cible IS NOT NULL) THEN
        RAISE EXCEPTION 'La regle % attend une cible capteur', NEW.id_regle_alerte
            USING ERRCODE = 'check_violation';
    END IF;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_alerte_cible_portee
BEFORE INSERT OR UPDATE OF id_regle_alerte, id_equipement_cible, id_capteur_cible
ON alerte
FOR EACH ROW
EXECUTE FUNCTION verifier_cible_alerte();

CREATE INDEX ix_batiment_id_campus
    ON batiment (id_campus);
CREATE INDEX ix_zone_id_batiment
    ON zone (id_batiment);

CREATE INDEX ix_hze_zone
    ON historique_zone_equipement (id_zone);
CREATE INDEX ix_hze_equipement_debut
    ON historique_zone_equipement (id_equipement, date_debut DESC);

CREATE INDEX ix_ace_equipement
    ON affectation_capteur_equipement (id_equipement);
CREATE INDEX ix_ace_capteur_debut
    ON affectation_capteur_equipement (id_capteur, date_debut DESC);

CREATE INDEX ix_mesure_capteur_evenement
    ON mesure (id_capteur, horodatage_evenement DESC)
    INCLUDE (valeur, unite, qualite, horodatage_reception);
CREATE INDEX ix_mesure_capteur_reception
    ON mesure (id_capteur, horodatage_reception DESC);

CREATE INDEX ix_alerte_equipement_etat_date
    ON alerte (id_equipement_cible, statut, date_creation DESC)
    WHERE id_equipement_cible IS NOT NULL;
CREATE INDEX ix_alerte_capteur_etat_date
    ON alerte (id_capteur_cible, statut, date_creation DESC)
    WHERE id_capteur_cible IS NOT NULL;
CREATE INDEX ix_alerte_regle_date
    ON alerte (id_regle_alerte, date_creation DESC);
CREATE INDEX ix_alerte_mesure_declencheuse
    ON alerte (horodatage_mesure_declencheuse, id_mesure_declencheuse)
    WHERE id_mesure_declencheuse IS NOT NULL;

CREATE INDEX ix_intervention_equipement_statut_date
    ON intervention (id_equipement, statut, date_ouverture DESC);
CREATE INDEX ix_intervention_demandeur
    ON intervention (id_demandeur)
    WHERE id_demandeur IS NOT NULL;
CREATE INDEX ix_intervention_statut_date
    ON intervention (statut, date_ouverture DESC);

CREATE INDEX ix_ati_technicien
    ON affectation_technicien_intervention (id_technicien, date_affectation DESC);
CREATE INDEX ix_ati_intervention
    ON affectation_technicien_intervention (id_intervention);
CREATE INDEX ix_lai_intervention
    ON lien_alerte_intervention (id_intervention);

COMMIT;
```

### 3.4 Validation de la portée de la cible d’alerte

Le `CHECK` de la table `alerte` garantit l’exclusivité équipement/capteur, mais un `CHECK` PostgreSQL ne peut pas consulter la table `regle_alerte`. Le déclencheur inclus dans le script complète l’intégrité référentielle en refusant une alerte dont la cible ne correspond pas à la portée de sa règle. Une version de règle publiée doit ensuite être considérée comme immuable; une modification de portée exige une nouvelle version. La protection de cette immutabilité doit être ajoutée au processus d’administration ou par une règle SQL dédiée si elle doit être garantie en base.

## 4. Indexation ciblée

### 4.1 Mesures IoT

| Index | Colonnes | Utilisation |
|---|---|---|
| `ix_mesure_capteur_evenement` | `(id_capteur, horodatage_evenement DESC) INCLUDE (valeur, unite, qualite, horodatage_reception)` | Lecture des séries d’un capteur sur une période et recherche de sa mesure la plus récente; `INCLUDE` permet certains parcours couvrants sans grossir les clés de tri. |
| `ix_mesure_evenement_brin` | `(horodatage_evenement)` | Filtrage temporel global et élagage des partitions; l’index B-tree local aide pour les plages plus fines à l’intérieur des partitions. |
| `ix_mesure_capteur_reception` | `(id_capteur, horodatage_reception DESC)` | Diagnostic du retard de transmission et recherche par date d’arrivée. À conserver uniquement si ces requêtes sont utilisées, car tout index accroît le coût d’ingestion. |

Les partitions mensuelles limitent les lectures historiques à la période pertinente grâce au *partition pruning*. L’index `(id_capteur, horodatage_evenement)` est créé localement dans chaque partition par l’index déclaré sur la table partitionnée.

Exemple de lecture d’état courant pour un capteur :

```sql
SELECT id_capteur, id_mesure, horodatage_evenement,
       horodatage_reception, valeur, unite, qualite
FROM smartcampus.mesure
WHERE id_capteur = :id_capteur
ORDER BY horodatage_evenement DESC
LIMIT 1;
```

Pour l’état courant de tout le parc, la fréquence d’actualisation visée (5 minutes) et le faible nombre de capteurs (environ 600) permettent de commencer par une requête `DISTINCT ON (id_capteur)` ordonnée par capteur et horodatage descendant. Si la latence mesurée ou le coût d’agrégation l’exige, une projection `etat_courant_capteur` peut être maintenue à l’ingestion; elle constitue alors une vue/projection dérivée, à synchroniser transactionnellement, et non une seconde vérité source.

Exemple de requête de diagnostic historique :

```sql
SELECT horodatage_evenement, valeur, unite, qualite
FROM smartcampus.mesure
WHERE id_capteur = :id_capteur
  AND horodatage_evenement >= :debut
  AND horodatage_evenement < :fin
ORDER BY horodatage_evenement;
```

### 4.2 Référentiel, relations et états

- Indexer les clés étrangères fréquemment utilisées en jointure ou pour les suppressions/mises à jour référentielles : bâtiments par campus, zones par bâtiment, historiques par zone, affectations par équipement, interventions par équipement/demandeur et participations par technicien/intervention.
- Les clés étrangères vers un parent ne créent pas automatiquement d’index sur la table enfant dans PostgreSQL; les index sont donc ajoutés explicitement lorsque les parcours prévus le justifient.
- Les index `(id_equipement, statut, date_ouverture DESC)` et `(statut, date_ouverture DESC)` servent aux listes d’interventions actives et aux files de traitement.
- Les deux index partiels d’alerte permettent de filtrer par cible et état sans indexer une valeur de cible nulle; l’exclusivité des cibles est assurée par le `CHECK`.
- Les identifiants uniques, codes, courriels et références sont indexés par leurs contraintes `PRIMARY KEY`/`UNIQUE`; ne pas créer un doublon manuel de ces index.
- Les contraintes d’exclusion sur les périodes créent des index GiST pour la validation des intervalles. Les B-tree `(id_entite, date_debut DESC)` restent utiles aux recherches de période et à la sélection du rattachement courant.

Les index doivent être confirmés sur les plans `EXPLAIN (ANALYZE, BUFFERS)` avec des volumes et distributions représentatifs. Les index inutilisés sont à retirer; ceux portant sur les mesures doivent être limités, car leur coût de maintenance touche les quelque 20 insertions/s nominales et les rafales de reconnexion.

## 5. Volumétrie, performance et exploitation

### 5.1 Ordre de grandeur

Avec 600 capteurs et une mesure toutes les 30 secondes :

- **20 mesures/s** en moyenne;
- **1 728 000 mesures/jour**;
- **630 720 000 mesures/an** sur 365 jours, avant retransmissions;
- mesures brutes retenues pendant 12 mois, selon la politique de rétention de l’étape 1.

Cette charge est modérée en débit moyen mais importante en nombre de lignes. La conception limite les types aux valeurs nécessaires, utilise un `BIGINT` pour l’identifiant et évite les index secondaires non justifiés. `NUMERIC` offre une précision exacte mais coûte généralement plus cher qu’un flottant; si chaque grandeur le permet, une représentation entière mise à l’échelle ou `DOUBLE PRECISION` pourra être évaluée par benchmark avant de changer le contrat des données.

### 5.2 Partitionnement et rétention

- Le partitionnement **RANGE mensuel sur `horodatage_evenement`** rend les requêtes temporelles plus sélectives et la purge des données expirées exploitable par suppression/détachement de partitions, plutôt que par suppression massive de lignes.
- La tâche d’exploitation crée les partitions plusieurs mois à l’avance, surveille leur présence et applique la politique exacte de rétention (12 mois glissants ou mois civils, à confirmer).
- Une partition ne doit être supprimée qu’après prise en compte des alertes pouvant référencer ses mesures. La FK de la mesure déclencheuse vers `mesure` protège l’intégrité; elle peut empêcher le détachement/suppression d’une partition contenant des mesures encore référencées. Il faut donc décider si ces mesures sont conservées plus longtemps, si le lien est remplacé par une référence d’audit non FK, ou si les alertes concernées sont archivées/expurgées selon une politique validée.
- Le DDL crée les partitions allant du mois courant à douze mois après. Il ne met pas en place le planificateur de maintenance ni la purge automatique; ces opérations requièrent une politique d’exploitation et une vérification des dépendances avant toute suppression.

La PK physique composite inclut la clé de partition pour que l’unicité et les références de mesures soient vérifiables par PostgreSQL. L’identifiant `id_mesure` généré par séquence est globalement distinct dans les opérations normales, mais la garantie relationnelle de la base porte sur le couple `(horodatage_evenement, id_mesure)`. Tout consommateur qui conserve une référence durable à une mesure doit conserver les deux colonnes.

### 5.3 État courant et séries historiques

- **État courant** : l’index `(id_capteur, horodatage_evenement DESC)` permet de chercher le dernier événement d’un capteur sans parcourir sa série complète. `qualite` permet au service de distinguer la dernière mesure reçue de la dernière mesure valide, selon la règle d’état courant qui reste à confirmer.
- **État courant global** : un balayage indexé de l’ordre de 600 capteurs est un premier choix adapté au parc de référence. Une table/projection de dernière valeur n’est ajoutée qu’après mesure des temps de réponse et du coût réel.
- **Historique par capteur** : filtrer d’abord le capteur et l’intervalle de temps; le partitionnement élimine les mois hors période, puis l’index local ordonne et filtre les observations. Les agrégations multi-capteurs à grande échelle peuvent justifier des tables d’agrégats, non incluses au MCD.
- **Situation spatiale historique** : la zone à la date d’une mesure se retrouve par l’intervalle de `historique_zone_equipement` contenant l’horodatage d’événement, après résolution de l’équipement via `affectation_capteur_equipement`. Les contraintes d’exclusion rendent ces rattachements non ambigus à un instant donné.

## 6. Écarts et décisions avant mise en production

1. Confirmer le moteur et sa version; une migration vers un autre SGBD exige la réécriture des exclusions temporelles, du partitionnement et de certains index.
2. Valider `NUMERIC(20,6)` pour chaque type de mesure, les unités et les règles de conversion.
3. Définir les valeurs de statuts exactes et les transitions permises, notamment pour l’acquittement/clôture des alertes et le cycle de vie des interventions.
4. Spécifier l’identité de message et le périmètre de déduplication avant d’ajouter une contrainte unique.
5. Décider si les historiques de localisation et d’affectation ont des contraintes de période supplémentaires (continuité, période obligatoire pour les actifs en service, corrections rétroactives).
6. Résoudre la politique de rétention des mesures déclencheuses référencées par les alertes, afin que le partitionnement et la purge restent compatibles avec les clés étrangères.
7. Ajouter et tester une politique d’immutabilité des versions de règles publiées et de traçabilité des modifications administratives.
8. Mesurer les requêtes réelles avec `EXPLAIN (ANALYZE, BUFFERS)` avant d’ajouter des index ou une projection d’état courant.
